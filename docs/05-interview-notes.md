# 面试讲解要点

> 目标：把这个项目讲成“你真的做过、能复盘、能深挖”的项目，而不是背简历。

## 1. 30 秒项目介绍

“我用 Flask + SQLite 搭了一个可运行的 CRM/ERP 测试靶场，包含客户、线索、商机、合同、产品、采购、库存、销售、发票、多租户和角色权限。然后针对它做了完整的测试：44 条用例、20 个 pytest 接口测试、27 个 Postman/Newman 请求、14 个 Selenium UI 自动化、2 个 JMeter 压测场景。测试过程中发现并修复了并发超卖、跨租户负责人引用、重复收货/开票等 4 个缺陷，最后输出接口报告、Allure 报告和性能报告。”

**关键词：** 自建系统、完整链路、接口 + UI + 性能、真实缺陷、可复现报告。

## 2. 为什么自己搭系统？

- 现成的开源系统（Odoo/若依）部署重、数据不可控，面试时很难讲清每个字段和流程；
- 自建系统可以精确控制业务规则、角色权限和异常场景，方便造数和复现缺陷；
- 测试的重点不是“系统多复杂”，而是“你是否能设计测试、发现问题、定位根因、推动修复”；
- 代码、用例、报告都在仓库里，面试官可以现场看。

**如果被问“这不是真实企业项目吧？”** 可以坦诚回答：
“这是一个个人实战项目，系统是我自己写的，但业务模型参考了真实 CRM/ERP 的核心链路；测试用例、自动化脚本、缺陷和报告都是真实产出。我重点想证明的是测试方法和工作闭环，而不是系统规模。”

## 3. 系统架构（1 分钟）

- Flask 应用工厂 + Blueprint：`crm.py`、`erp.py`、`saas.py`、`api.py`；
- SQLite 存储，`schema.sql` 定义表结构，`seed.py` 造演示数据；
- Web 页面用 Jinja2 服务端渲染，接口用 REST + Session；
- 业务服务层 `services.py` 被 Web 和 API 共用，保证两条入口的业务规则一致；
- 关键规则：租户隔离（所有查询带 `tenant_id`）、角色权限（admin/sales/warehouse/finance）、订单状态机（draft→confirmed→shipped/received）、库存原子扣减。

**可以主动画的状态机：**

```
销售：draft → confirmed → shipped → 已开票
采购：draft → confirmed → received
异常：draft/confirmed → cancelled（shipped/received 不可取消）
```

## 4. 测试策略（为什么这样分层）

| 层次 | 目的 | 工具 |
|---|---|---|
| 接口 | 快速覆盖业务规则、参数校验、权限、数据一致性 | pytest + requests、Postman/Newman |
| UI | 验证关键用户路径、页面交互、菜单权限 | Selenium + Pytest + Allure |
| 性能 | 找瓶颈、给容量基线 | JMeter |
| 手工 | 补充探索性测试、异常场景 | 测试用例 |

**分层原则：**
- 业务规则优先放接口层，执行快、稳定、易定位；
- UI 只覆盖核心路径（登录、客户、订单、库存、权限），不做“全页面点点点”；
- 性能只压核心接口，先基线再梯度；
- 测试数据统一前缀，避免污染演示数据。

## 5. 自动化框架怎么讲

### 5.1 POM

- `BasePage` 封装显式等待、点击、填值、截图、alert 处理；
- `LoginPage`、`CustomersPage`、`SalesOrdersPage`、`PurchaseOrdersPage`、`InventoryPage` 按页面拆分；
- 测试用例只写业务动作，不写定位细节，页面改版只改 Page 对象。

### 5.2 稳定性

- 全部使用显式等待，不用 `sleep`；
- 等待“URL 变化 + 目标元素出现”，避免页面跳转时 stale element；
- 失败自动截图并附到 Allure；
- 测试数据用时间戳/UUID，避免重复；
- 对 `confirm()` 弹窗统一用 `accept_alert()` 处理。

### 5.3 pytest fixture

- `driver`：每个测试独立浏览器，保证隔离；
- `logged_in`：复用登录步骤；
- `api_admin`、`customer_factory`、`product_factory`：通过接口造数，UI 测试只关注被测流程；
- `pytest_runtest_makereport`：失败时自动截图。

## 6. 四个缺陷故事（STAR，重点背）

### 6.1 并发发货超卖（DEF-002）

- **S**：产品库存 5，创建 8 个已确认销售订单，每个数量 1；
- **T**：验证并发发货不会超卖；
- **A**：用 8 个线程并发调用发货接口；代码审查发现“先查库存再扣减”的 check-then-act；
- **R**：原实现可能超卖/负库存；改成条件状态迁移 + 原子扣减 `UPDATE ... WHERE stock>=qty` + WAL/busy_timeout；回归结果 5 成功、3 失败、库存 0。

### 6.2 跨租户负责人（DEF-001）

- **S**：租户 A 管理员更新客户；
- **T**：验证不能把租户 B 的用户设为负责人；
- **A**：构造 `owner_id=5`（租户 B 用户）调用更新接口；
- **R**：原实现返回 200，存在跨租户引用；补租户校验后返回 400，并加回归用例。

### 6.3 重复收货/重复开票（DEF-004）

- **S**：采购订单已确认，连续/并发调用收货；
- **T**：库存只能增加一次；
- **A**：构造重复请求，检查状态迁移与库存；
- **R**：原实现状态校验不是原子操作；改成 `WHERE status='confirmed'` 条件更新 + 发票唯一约束；重复请求返回 400。

### 6.4 负库存/负价格（DEF-003）

- **S**：产品创建接口；
- **T**：验证边界值；
- **A**：传入 `stock=-1`、`price=-1`；
- **R**：原实现直接写入；补非负校验后返回 400。

## 7. 性能怎么讲

- 混合场景：20 线程、600 请求、0 错误、55.3 req/s；
- 登录平均 147ms、P95 168ms；查询/创建 P95 6–15ms；
- 销售订单创建：10 线程、200 请求、0 错误、34.3 req/s，订单创建 P95 8ms；
- **瓶颈分析**：登录耗时来自密码哈希；查询/写入很快；SQLite 写锁是潜在瓶颈；生产建议 Gunicorn 多 worker、连接池、Token/会话复用、缓存、MySQL/PostgreSQL。
- **注意**：这是本地单机基线，不说“支撑多少用户”，只说“在这个环境下测得多少”。

## 8. 高频追问与回答

**Q：为什么用 POM？**
A：把页面定位和业务动作分离，脚本可维护；页面改版只改 Page 对象；测试用例可读性更高。

**Q：显式等待、隐式等待、强制等待的区别？**
A：显式等待针对某个条件轮询；隐式等待是全局查找元素的超时；强制等待是 sleep。自动化里优先显式等待，避免 sleep 导致慢和 flaky。

**Q：怎么处理 stale element？**
A：页面跳转/局部刷新会让旧元素失效；等待 URL 或目标元素重新出现，并在等待条件里捕获 `StaleElementReferenceException` 重试。

**Q：接口测试怎么校验数据一致性？**
A：不仅看响应码/字段，还查数据库或再调详情接口；例如发货后查库存、开票后对比订单金额与发票金额。

**Q：怎么测权限？**
A：三个层次：菜单是否可见、接口是否 403、数据是否越权（租户 404 / 只能看自己的数据）。本项目覆盖前两层 + 租户隔离；数据范围（owner-based）是已知扩展点。

**Q：怎么测并发？**
A：先用 JMeter 做并发基线，再用 pytest + ThreadPoolExecutor 做业务并发断言；关注成功数、最终库存、订单状态、错误率。

**Q：怎么保证测试数据不污染？**
A：统一 `QA-`/`PERF-` 前缀；测试后归档/删除；需要干净环境时 `python -m app.seed` 重建。

**Q：这个项目还有什么不足？**
A：SQLite/Flask 开发服务器不适合生产；没有 CSRF、登录限流；数据权限只做到租户级；性能只做本地基线；下一步会补 CI/CD、契约测试、安全测试和更大并发梯度。
