## DEF-001 客户更新未校验负责人租户归属

**模块：** CRM / 客户 API  
**级别：** P1（高）  
**状态：** 已修复  
**发现方式：** 接口测试 + 代码审查

**前置条件：**
- 租户 A 管理员 `admin` 已登录；
- 租户 A 存在客户 `C`；
- 租户 B 存在用户 `U`（id=5）。

**复现步骤：**
1. 调用 `PUT /api/customers/{C}`；
2. 请求体传入 `{"owner_id": 5}`（属于租户 B 的用户）。

**预期结果：** 返回 400，提示负责人不属于当前租户。  
**实际结果：** 原实现直接保存，客户 `C` 的负责人被设置为租户 B 的用户，存在跨租户数据引用风险。

**根因：** 客户创建接口校验了 `owner_id` 的租户归属，但更新接口漏掉了同样的校验。

**修复：**
- 在 `customers_update` 中校验 `owner_id` 是否属于当前租户；
- 增加回归用例 `test_customer_update_owner_cross_tenant`。

**回归结果：** 通过。跨租户负责人返回 400，同租户负责人可正常保存。

## DEF-002 并发发货存在超卖/负库存风险

**模块：** ERP / 销售订单发货  
**级别：** P1（高）  
**状态：** 已修复  
**发现方式：** 并发测试 + 代码审查

**前置条件：**
- 产品 `P` 库存为 5；
- 创建 8 个销售订单，每个数量 1；
- 8 个订单都已确认。

**复现步骤：**
1. 使用 8 个线程并发调用 `POST /api/sales-orders/{id}/ship`；
2. 观察成功数量与最终库存。

**预期结果：** 最多 5 个订单发货成功，库存变为 0，不能出现负库存。  
**实际结果：** 原实现采用“先查询库存、再更新库存”的 check-then-act 模式，并发下多个请求可能同时通过校验，导致超卖或库存更新丢失。

**根因：**
- 库存校验与扣减不是原子操作；
- 订单状态迁移没有条件更新，存在重复发货窗口；
- SQLite 默认未开启 WAL/busy_timeout，并发写容易锁等待。

**修复：**
- 发货前使用条件更新完成状态迁移：`WHERE status='confirmed'`；
- 库存扣减改为原子 SQL：`UPDATE products SET stock=stock-? WHERE id=? AND stock>=?`；
- 校验 `rowcount`，失败则回滚；
- 数据库连接开启 WAL 与 `busy_timeout=10000`；
- 增加并发回归用例 `test_concurrent_shipping_no_oversell`。

**回归结果：** 8 个并发请求中 5 个成功、3 个返回 400，最终库存 0，无负库存。

## DEF-003 产品创建允许负价格、负库存

**模块：** ERP / 产品 API  
**级别：** P2（中）  
**状态：** 已修复  
**发现方式：** 边界值测试

**复现步骤：**
1. 调用 `POST /api/products`；
2. 请求体传入 `{"sku":"QA-NEG","name":"负库存产品","stock":-1}`。

**预期结果：** 返回 400，提示价格/库存不能为负数。  
**实际结果：** 原实现直接写入，产生负库存产品，后续销售/库存逻辑会出现异常数据。

**修复：**
- 对 `price`、`cost`、`stock`、`safety_stock` 做数值与非负校验；
- 增加回归用例 `test_product_validation`。

**回归结果：** 通过，负库存/负价格返回 400。

## DEF-004 重复收货/重复开票缺少幂等控制

**模块：** ERP / 采购收货、发票  
**级别：** P2（中）  
**状态：** 已修复  
**发现方式：** 场景测试 + 并发测试

**复现步骤：**
1. 创建并确认采购订单；
2. 连续/并发调用两次 `POST /api/purchase-orders/{id}/receive`；
3. 观察库存是否被增加两次。

**预期结果：** 第二次收货返回 400，库存只增加一次。  
**实际结果：** 原实现先读取状态再更新，两个请求可能同时通过状态校验，导致重复入库；发票也存在重复开具窗口。

**根因：** 状态迁移不是原子操作；发票缺少唯一约束。

**修复：**
- 收货使用条件状态迁移：`WHERE status='confirmed'`，`rowcount=0` 时拒绝；
- 发票表增加 `UNIQUE(sales_order_id)`，并在服务层先查重；
- 增加回归用例：重复收货、重复开票。

**回归结果：** 通过。重复收货/重复开票均返回 400，库存与发票金额只记录一次。

## DEF-005 缺少 CSRF Token（已知限制）

**模块：** Web 表单  
**级别：** P3（低）  
**状态：** 已知限制

**描述：** 系统使用 Session Cookie 登录，但表单未加 CSRF Token。攻击者若诱导已登录用户访问恶意页面，可能伪造客户创建、订单确认等请求。

**影响：** 仅影响浏览器表单；API 使用 JSON + Session，同样需要防护。当前项目定位为本地测试靶场，未实现 CSRF。

**建议：** 生产环境引入 Flask-WTF CSRFProtect，或在 API 层增加 CSRF Header/Token 校验。

## DEF-006 登录无失败次数限制（已知限制）

**模块：** 登录  
**级别：** P3（低）  
**状态：** 已知限制

**描述：** 登录接口未做失败次数限制、验证码或账号锁定，存在暴力破解风险。

**建议：** 生产环境增加登录失败计数、账号锁定、验证码或 MFA；同时对登录接口做限流。

## 缺陷分析小结

- 4 个已修复缺陷中，2 个属于**并发/幂等**问题（DEF-002、DEF-004），是 ERP 系统最常见、也最能体现测试深度的类型；
- 1 个属于**多租户数据完整性**问题（DEF-001），体现了权限测试不能只看菜单，还要看接口参数；
- 1 个属于**输入校验**问题（DEF-003），适合用边界值/等价类覆盖；
- 2 个已知限制（CSRF、登录限流）属于生产化前必须补齐的安全项，已在测试报告中说明。
